# External review, 2026-11-05 — findings and what was done

A read-only review of the plugin (DeepSeek v4.1 via OpenRouter, one subagent, no shell access to the
wallet) produced a prioritised list. Every finding below was re-checked against the code before it was
touched: one of them — the XRP parity bug — invalidated a "verified" claim in this repo, so the first
lesson is that a test which agrees with the implementation proves nothing.

## Fixed

| # | Finding | What was wrong | Fix |
|---|---|---|---|
| 1 | **XRP address parity (critical)** | the compressed-pubkey prefix took the parity of `x[-1]` instead of `y[-1]`, so about half of all XRP addresses belonged to no key. Our own "cross-check" against xrpl-py compared the same wrong input, so it passed. | parity from `public[-1]`; vectors regenerated from `ecdsa`'s point arithmetic + xrpl-py's `encode_classic_address`. `tests/test_xrp.py` now pins `rQrFNn…`, `rQ96gj…`, `rBgGZ9…` |
| 2 | **`fee_cap` was never persisted** | `Settings.to_dict()` omitted it, so `config set fee_cap=…` wrote a signed file without it, reported success, and the next unlock restored the shipped default | `fee_cap` and `http_timeout_seconds` are serialised; a cap the operator tightened stays tightened |
| 3 | **the cap was not checked where money is signed** | only `request_tx` checked it; `approve()` rebuilds a plan after a restart, and the EVM adapter re-reads gas at broadcast | `_broadcast` refuses any plan whose fee exceeds the cap, before signing |
| 4 | **a failed broadcast was recorded `approved`** | the approval was already consumed, so the payment could never be retried, and every reader saw "approved" for money that never moved | status `failed`, ledger entry says `denied`, the human can approve again |
| 5 | **an emptied ledger still verified** | delete `ledger.jsonl` + anchor and `verify` said "no receipts yet" | with a keystore present, zero entries is a failure: `initialize()` always writes one |
| 6 | **archiving twice in a second destroyed an archive** | second-resolution filename + `os.replace` overwrote the previous chain | filenames get a suffix until unique |
| 7 | **one-time sandboxes could never self-destruct** | after the first sweep `spent = budget`, so `remaining()` was 0, the next sweep returned "nothing to sweep" with no transfer, and the reaper read that as a failure forever | sweeps read the **live account balance**, and "nothing left to sweep" is the goal state, not an error |
| 8 | **a sweep could be pointed anywhere** | `sweep_of` bypasses the budget check (it is not a spend), so a crafted request could empty a sandbox to an arbitrary address | a sweep must pay *this wallet's own address* for that chain, checked before policy |
| 9 | **`wallet_import` replaced the wallet on operator scope alone** | the operator token is readable by anything running as this uid | import now needs the passphrase, `confirm: true`, and a zero balance |
| 10 | **widening a sandbox's profile list had no gate** | `allowed_profiles: []` = every profile, changeable without a secret | tightening is free; adding a profile or clearing the list needs the passphrase |
| 11 | **`pay_url` was an SSRF with a caller-controlled timeout** | the agent supplies any URL, `urlopen` followed redirects, and the fetch ran inside the mutation lock | public addresses only (`is_private/loopback/link_local/reserved` refused), redirects refused, timeout clamped to 15 s |
| 12 | **the pane retried every failed POST** | a timeout could file the same payment twice | retry only when the failure looks like a body-shape rejection, which is the only thing the retry was for |
| 13 | **errors vanished within 3 s** | the 3 s poll cleared `error` | the next action clears it, not the clock |
| 14 | **three controls that could never work** | contact delete/edit sent no passphrase, mandate actions read a passphrase from a form, header auto-lock sent a passphrase that `act()` had just cleared | visible passphrase rows for Contacts and Autopay with two-step delete; auto-lock is now gated *directionally* — shortening the window is free, lengthening it or turning it off needs the passphrase |
| 15 | **first-run passphrase had no confirmation** | one field, on a wallet with no recovery | typed twice, and a mismatch is refused before a keystore exists |
| 16 | **`/nodes` did not exist** | Settings showed "no endpoints known" forever | route added; the API contract test now also scans `ctx.rest()` |
| 17 | **daemon crashes surfaced as HTTP 400** | `internal_error` read as "your request was wrong" | mapped to 500 |

`tests/test_api_contract.py` (new) exists because this repo shipped the same bug twice — a Pydantic
body that lost a field its handler still read, and a route added after the backend started. It parses
`plugin_api.py` and `state.py` and fails on: a route calling an unregistered daemon method, a handler
reading an undeclared `body.<field>`, or the pane calling a route the router does not serve.

## Not fixed, on purpose (with reasons)

- **A sandbox ACL trusts the profile the caller declares.** `request_tx` copies `params["profile"]` and
  `_sandbox_decision` authorises on it, so an agent with a shell can claim any profile name. Fixing it
  properly means deriving the profile in the daemon from `SO_PEERCRED` + `/proc/<pid>/environ`, which
  is wrong under multi-profile serving (one process, many sessions), or minting a token per profile.
  Both are real work and one is a design change. Until then the ACL is **cooperative**: it stops a
  misconfigured agent, not a hostile one with shell access to the same uid. Stated here rather than
  assumed away.
- **The operator token is readable by anything running as this uid.** That is the plugin's documented
  threat model (HARDENING.md): the boundary is the OS user. Every operator-only action that changes
  standing authority now needs the passphrase as well, which is the only thing that survives a
  compromised uid short of a second machine.
- **The signer RPC password is on the command line** (`--rpc-login user:pass`), visible in
  `/proc/<pid>/cmdline` to the same uid. Same-user visibility makes this strictly redundant, and
  `monero-wallet-rpc` has no env/file form for it. The 0600 `wallet.env` path is the least-bad option;
  the README should not imply more. *(Corrected 2026-11-12: the binary does take every option
  from `--config-file`, so the login is now a 0600 `signer.conf` and argv carries no secret.
  Same-uid readability of the file — and of the signer itself — is unchanged.)*
- **Archived chains are not walked by `verify`.** The current chain is; the archive link is recorded
  but not yet re-verified. Noted in UPDATE-SAFETY.md as a known gap rather than silently implied.
- **Addresses are served from `addresses.json` while locked** — deliberate. A receiving address is
  public data, and a wallet that cannot show you an address to be paid at is broken. Balances are not
  served while locked.

## Features the review suggested, ranked (not built yet)

1. **Fiat estimate + decoded intent on the approval card** (M) — the human gate is only as strong as
   the sentence above the button; "0.0042 XMR" means nothing to most approvers without "≈ €4.10".
2. **Address-poisoning guard** (S) — flag a payee within a few characters of a known contact or a past
   recipient. This UI shape (show address, copy, approve) is exactly what that attack targets.
3. **Dry-run button** (S) — plan the transfer, run policy, show the fee, sign nothing.
4. **Per-payee spend view** (M) — caps consumed vs left, one row per payee.
5. **Seller/accept mode over x402** (L) — `receive_address` + `verify_payment` already exist; being
   paid is the other half of an agent wallet.

Rejected as out of scope: on-chain policy / ERC-4337 session keys (a v2 research project),
Lightning/L402 (already refused honestly), a self-updater (its absence is the control), moving the
ledger to a database (the hash chain is the point).

# Second pass, same day — after the guarantee work

A second read-only review was pointed at the *new* code (the `_broadcast` choke point,
`authorised_by`, the sweep bypass, one-time teardown, coin/network derivation, load-time expiry, the
XRP fix, the pane's coin-first forms). It confirmed the main claims — one choke point, approvals
no replay, lock really clears adapters, coin↔chain derivation, XRP parity, expiry cannot hit an
in-flight approval — and then found twelve more things. Fixed:

| # | Finding | Fix |
|---|---|---|
| 1 | **x402 `submit()` was an SSRF with a signature attached** — it skipped the public-host check and followed redirects, and the URL comes from the request, which an agent can influence. A prompt-injected agent could have the daemon GET `127.0.0.1:9119` with a valid EIP-3009 authorisation in `X-PAYMENT`. | `_public_host()` + no-redirect opener in `submit`, timeout clamped. |
| 2 | **The fee cap was checked against a stale price** — `EvmAdapter.broadcast` re-reads gas and re-signs, so a repriced or hostile RPC set the price after the cap check. | `broadcast(plan, fee_cap=…)` refuses before signing when `gas × maxFeePerGas` exceeds the cap; `_broadcast` passes it in. |
| 3 | **A "sweep" closed a sandbox no matter what moved** — any tx tagged `sweep_of` set `spent = budget; enabled = False`, so a 0.001 self-payment from a 0.4 budget closed it with 0.399 stranded and unreachable. | After the transfer the live balance is re-read; the sandbox closes only when it is actually empty, otherwise a `swept_partial` receipt records what is left and it stays open. |
| 4 | **Sweeps were policed as spends** — a lowered `per_tx_cap` or a payee allowlist could deny a sweep, and the reaper then retried every 20 s forever. | `SpendContext.self_transfer`: a transfer to our own address bypasses per-tx/daily caps and the allowlist (chain and asset scope still apply). |
| 5 | **Deny stopped working after the approval TTL** — the request could be neither approved nor denied, and the pane showed a Decline that always errored. | `deny()` accepts an unused approval regardless of expiry; an approval that has expired ages the request to `expired`. |
| 6 | **Destruction read the *unlocked* balance** — change from the one-time payment can still be confirming, so a sandbox could be destroyed with money in flight. | `total_balance_at()` (including unconfirmed) is used for the destroy decision; spending still uses the unlocked figure. |
| 7 | **Adding a new chain to an existing contact needed no passphrase** — "send Aiden 5 USDC" could resolve to an address the human had never seen for that chain. | Any new address on an existing contact requires the passphrase, exactly like changing one. |
| 8 | **Enabling a coin required no secret** — it adds a chain and a signing surface. | Recorded in the ledger as `coins_changed` with what was enabled/disabled. Deliberately not passphrase-gated: enabling a coin grants no authority to spend (that still needs approval), and gating it would break the header coin menu. |
| 9 | **"save access" could never widen a sandbox ACL** — it posted no passphrase. | The Sandboxes section has a passphrase row, and the button sends it. |
| 10 | **Expiry at load time wrote no receipt** (`__init__` has no ledger key). | Expired ids are queued and the receipts are written on the next unlock. |
| 11 | **`mandates_propose` could overwrite an active mandate** with an inert proposal — a delete that `mandates_delete` passphrase-guards. | A proposal naming an existing mandate is refused (`mandate_exists`). |
| 12 | **The pane's POST retry matched any error mentioning "json"/"body"**, so an HTML bridge page could file a second request. | Retry only on a real 422/unprocessable; `/request` now carries an idempotency key generated once per submission. |

Also: the approval card now says when a payment is **funding a sandbox** ("approving this hands that
budget to the agent, which can then spend it without asking again") and when it is a **sweep home**,
and `sandbox_sweep` no longer requires the sandbox to be enabled — recovering dust from a closed one
is always safe because the destination is our own address.

Tests: 160, including regressions for each item above (`test_a_partial_sweep_does_not_close_the_sandbox`,
`test_a_sweep_is_not_policed_as_a_spend`, `test_deny_still_works_after_the_approval_window`,
`test_adding_a_new_chain_to_a_contact_needs_the_passphrase`,
`test_a_proposal_cannot_overwrite_an_existing_mandate`,
`test_gas_repricing_cannot_beat_the_fee_cap`,
`test_submit_refuses_a_private_host`).

Still open (stated, not fixed): the EVM gas clamp is a refusal rather than a re-price, EVM/Live-chain
behaviour is unverified without network, and the sandbox ACL still trusts the profile name the caller
declares (per-profile tokens remain the real fix).

# Third pass + update-proofing + design, same evening

Three reviewers ran in parallel (design, Hermes-update robustness, security #3). All three found
things; everything below is fixed.

## Security (#3)

| # | Finding | Fix |
|---|---|---|
| 1 | **The signer endpoint was repointable without the passphrase.** `monero_rpc_url` was not in `SENSITIVE_KEYS`, so with the operator token anyone could point the XMR signer at their own host: the wallet would then report *their* address for the human to fund, send the signer's basic-auth credentials there, and validate a later sweep's "our own address" against it. | All three signer keys are sensitive (passphrase), and `monero_rpc_url` must be loopback — a remote endpoint receives the signer's credentials. |
| 2 | **The sandbox ACL passphrase was dropped by Pydantic** — `SandboxProfiles` had no `passphrase`, so widening an ACL could never work and the pane's passphrase row was a decoy. | Field added and forwarded. |
| 3 | **`/request` dropped the `idempotency_key`** the pane generates. | Forwarded, so the duplicate-payment guard covers the UI too. |
| 4 | **A failing auto-path broadcast left `approved` behind.** Auto-lock firing mid-broadcast turned a mandate payment into a request that says approved, with an intent receipt and no outcome. | Wrapped: `failed` (or back to `pending` when the wallet locked) plus a denial receipt. |
| 5 | **An unreadable balance closed a funded sandbox as "swept".** | `live is None` no longer closes it; the sandbox stays open and the receipt says so. |
| 6 | **First-run keystore creation is unauthenticated.** Whoever reaches the socket before the operator's first setup owns the master secret. | Documented as the same-uid limitation (per-process separation is the fix); the creation receipt records that it came over the API. |
| 7 | **Sandbox budget debited after the broadcast.** A crash in that window could replay the budget after a restart. | Still debited after the send (the send can fail), but the `broadcasting` intent is already in the ledger — documented as the recovery path. |
| 8 | **`requests_list` re-issued an approval on every poll**, so a dead request stayed approvable. | The window is measured from the request: past it the request becomes `expired`. |
| 9 | **`ledger_archive` is token-only.** | Kept (it archives, it does not delete) — the archive stays on disk with its signature chain, and `ledger_verify` still walks the live one. Noted in UPDATE-SAFETY. |

Also fixed while in there: `/mandates/revoke` was **dropping the passphrase** (so revoking an autopay
from the pane always failed) and called the daemon with *agent* scope. The contract test below caught it.

## Update-proofing

| Finding | Fix |
|---|---|
| `dashboard/plugin_api.py` did `sys.path.insert(0, …)` inside the web server process, shadowing any app module named `wallet`/`dashboard`. | `append`. |
| `requirements.txt` listed only PyNaCl, so an install from it could not derive a BTC address. | Mirrors `plugin.yaml`, with `eth-keys` declared directly instead of relied on as an eth-account transitive. |
| `_pick_python()` probed only PyNaCl; a python with PyNaCl but no eth-account won the probe and then reported chains offline. | Probes every runtime import (`eth_account`, `eth_keys`, `embit`). |
| An old daemon answered `unknown_method`, which the dashboard mapped to **HTTP 400** — a build skew read as a policy refusal. | The client raises `stale_walletd: …restart it`; the API maps that to **503**. |
| A keystore from a newer build was reported as "unreadable" — i.e. your keys are gone. | `keystore_too_new` with "upgrade the plugin instead of downgrading it". |
| One rejected `register_tool` kwarg (a renamed `emoji`) failed the whole plugin. | Per-tool registration with argument retry; skipped tools are reported. |
| `lastArchive.details.entries` was unguarded — an older archive entry blanked the Receipts tab. | Optional access. |
| `host.navigate` was called unguarded. | `typeof` check. |
| Unknown manifest field `provides_middleware`, unset `manifest_version`. | Dropped/added; `validate` now reports only the known `crypto_mining` false positive. |

Still open (stated): one `wallet_home()` resolver across five call sites, and regenerating the systemd
unit when the plugin path moves.

## Design

- The amount sits next to the coin (coin, name, amount, chain on the left; only the status pill right).
- Responsive Tailwind breakpoints (`xl:grid-cols-2`, `lg:grid-cols-2`) removed from rows/cards: they
  fire on **viewport** width, and this page lives in a 600px pane, so they produced overflowing
  2-up rows.
- The approval card is now the heaviest element on the page: 3px amber border, coin-tinted wash,
  30px coin-coloured amount, "pay to" label with a shortened address (full value in the tooltip).
- Typography floor raised from 10px to 11px; card borders toned down (0.70 → 0.34 alpha) so the
  per-coin accent carries the colour instead of every border shouting.
- Page order is now hero → Assets → Pending approvals → New request: balances and the thing needing a
  decision come before the form.
- States: a null balance reads `locked`/`offline` instead of a lone em dash, an RPC error appears in
  the row's subline (it was silently ignored while a stale balance was shown as live).
